# Account Sync

RainFlix uses Supabase Auth and PostgreSQL for optional Windows/Android account sync. Local playback and personalization work without an account or network connection. The static website and GitHub Pages hosting do not require a RainFlix server. Accounts live at **Settings -> Account & sync** (`/settings/account`) in native apps. The Google button uses Google's supplied multicolor logo on white. The ordinary web catalog has no account Settings UI.

## Activate the project

1. Open the Rainflix Supabase project and its SQL Editor.
2. Run [the migration](../../supabase/migrations/202610150001_account_sync.sql) once. This creates the records table, owner-only row-level security, and atomic merge function. Do not disable RLS.
   Then run the contents of [the add-on sync migration](../../supabase/migrations/202610150002_addon_sync.sql). This extends the existing merge function to accept add-on registrations; do not paste the file path into the SQL Editor.
3. In Google Cloud Console, create/select a project, configure Google Auth Platform branding/audience, and add your Google account as a test user while the OAuth app is in Testing. Create an OAuth client of type **Web application**. This is a Supabase-hosted OAuth flow, not an embedded Google sign-in widget or Android-specific client.
4. Set the Google client's authorized redirect URI to `https://wrsyztvvrpkckqbqtstz.supabase.co/auth/v1/callback`. In Supabase -> Authentication -> Sign In / Providers -> Google, enable Google and enter the Google client ID and client secret. Store the secret only in Supabase. No SMTP or email template changes are needed for this sign-in method.
5. The project URL and publishable key are configured in `scripts/config.js` under `account`. Never put a Supabase secret/service-role key or database password there.
6. In Supabase -> Authentication -> URL Configuration -> Redirect URLs, add `rainflix://auth/callback**`. The wildcard permits the random attempt query parameter; the app accepts only the exact host/path. For the local desktop-layout browser preview, also allow `http://127.0.0.1:5174/**`. Do not put either of these in Google's authorized redirect URI list; Google redirects to Supabase, which redirects to RainFlix.
7. Rebuild and install Windows/Android to register the app protocol. Open Settings -> Account & sync -> Continue with Google. Complete sign-in in the system browser and allow it to open RainFlix. Signing in automatically merges and syncs this device, including restored sessions. All five categories default on; users can choose My List, Continue Watching/progress, watched history, shared playback/subtitle preferences, and installed add-ons individually, including before sign-in. Choices are per device/account. There is no separate merge/enable or pause button; use category switches or sign out to stop syncing.
8. Check that a saved title and playback position move between two devices signed into the same account. Verify a different account cannot read those records before publishing. Publish the Google OAuth consent configuration appropriately before public release; test-user-only mode is not a general release configuration.

The owner reported applying both migrations on October 15, 2026. Anonymous live requests to both the table and merge function returned 401 permission denied, as expected. Authenticated cross-account isolation and real Google sign-in have not been verified live. Local tests mock Supabase; complete these live checks before release. Google provider configuration has not been independently verified. The earlier email-code UI was replaced; SMTP is no longer a prerequisite.

## Google callback handling

Google opens in the system browser via the native opener. Supabase uses PKCE; its verifier and a random ten-minute sign-in attempt live in IndexedDB so a cold-start callback can finish on the initiating device. Callback tokens are not accepted from URL fragments. The app checks the exact `rainflix://auth/callback` route, attempt nonce and expiry before exchanging a one-time code. Codes/verifiers are not logged or placed in the library sync journal. Windows reuses the existing single-instance protocol queue, and Android reuses its intent queue; the frontend routes auth callbacks separately from manifest installation. Existing add-on install links retain their validation. An app restart preserves the pending verifier; uninstalling/clearing storage does not.

In the desktop-layout browser preview (not Tauri), sign-in uses a same-origin callback instead of the app protocol. Startup consumes and removes callback parameters before returning to Settings. This is a development convenience; the normal web catalog still has no account Settings UI. Do not test a dev executable's callback against a separately installed release: their session/verifier stores may differ.

## Data and conflicts

Native startup begins account restoration under the existing RainFlix loader. A signed-in, online startup waits for installed add-on restoration and the first merge before revealing the initial route, so Home can render the synced library/progress. Signed-out and offline devices continue locally without a cloud request. Failed sync releases the loader with local data; a separate 30-second startup deadline prevents stalled auth/storage/network work from trapping the UI. The normal minimum loader duration still applies. Explicit launch links retain their target route rather than being redirected to Home. The web catalog does not wait for account startup.

Migration `202610150003_user_document_sync.sql` changes the active table to **one row per user**, with a `records` JSONB document and `updated_at`. Library, progress, settings and add-on changes live inside this document. Per-item timestamps and deletion markers remain inside the JSON for safe offline merging. The RPC locks the user's row during merge and retains its existing response format for installed-client compatibility. Existing data is copied transactionally; `rainflix_sync_legacy` is retained as an inaccessible backup (all API-role grants revoked). Do not delete this backup until migration and device sync have been verified. Run migration 003 once after 001 and 002; do not rerun the earlier migrations afterward. No hosted schema changes are applied automatically by the app.

Sync covers My List, Continue Watching/history, watched titles and episodes, per-episode playback position, shared subtitle/audio language, subtitle appearance, auto-next/skip/preload/preview preferences, and HTTPS add-on registrations with enabled/disabled state and removals. Migration `202610150004_playback_preferences_sync.sql` also enables `playback/` records in the same user document: provider identity, a nonreversible exact-torrent-file fingerprint, quality and per-title subtitle/audio preferences. These follow the Continue Watching/progress category. A receiving device resolves its own installed provider ID and fetches fresh sources before automatic resume. Device animation/fullscreen/update-check settings, volume/mute, cache, service addresses, stream responses, signed playback URLs and raw torrent hashes remain local or memory-only. Artwork syncing is restricted to public TMDb images. Disabling a category stops its uploads and local application of remote changes; it does not delete existing cloud records. Re-enabling reconciles changes again.

The account UI shows sync enabled state without a last-sync timestamp. Sign out is always actionable, including during a request; it invalidates that request's ability to apply data and does not wait for the sync HTTP request to finish.

Add-on configuration links can contain private tokens. The account page discloses their cloud storage before sync is enabled. Add-on credentials are protected by authenticated owner-only RLS and HTTPS, **not end-to-end encryption**; do not describe this as a private encrypted vault. Locally, add-on sync journals and baselines use IndexedDB only, never localStorage or the service worker. Cloud record IDs are SHA-256 hashes of normalized URLs, not raw install links. Only registrations are copied, never manifest response payloads or streams. A receiving device fetches fresh manifests; unavailable servers retain an unavailable registration so catalog/playback still work. HTTP/local service registrations stay device-only. New-device initial add-on snapshots receive the lowest revision so seeded presets cannot resurrect a newer cloud deletion or override a newer enabled/disabled choice. Existing local registration IDs are preserved when URLs match; custom add-on metadata routes may still require their original provider ID, unlike TMDb/IMDb routes.

Each record has a millisecond edit timestamp. The atomic database merge keeps the latest edit per record and retains deletion markers so offline devices do not resurrect removed titles. Sign-in merges existing local records into the account automatically for selected categories. Conflicting edits to the same title use latest-edit-wins, not greatest playback position (rewinding is meaningful). Simultaneous watched-episode changes for the same title also use latest-edit-wins. Keep device clocks accurate; timestamps over five minutes in the future are rejected by the server.

Local changes are journaled immediately. Settings/library/add-on edits and explicit playback flushes upload after three seconds; ongoing playback checkpoints are batched at most once a minute. There is no idle polling or Sync now button. Sign-in/restoration, network reconnection, and returning to the app (at most once a minute) reconcile remote data. Only revisions not yet acknowledged by the server are uploaded. JSON object key order does not count as a change, and unchanged remote data is not rewritten or rebroadcast as storage changes. Requests time out after fifteen seconds. Failed requests keep the journal and retry on the next change/reconnect/return, not an endless timer. Safe error messages identify the failing stage and an allowlisted error code/name without exposing tokens or server payloads. This is change-driven sync, not live shared playback.

Auth sessions live in IndexedDB, not the add-on response cache. Account-specific nonsecret sync journals live in localStorage. RLS provides owner authorization and Supabase uses HTTPS, but this is not end-to-end encrypted library storage. Sign-out stops syncing and keeps the local library. Signing into another account also merges selected local data automatically: on a shared device, clear local history or disable categories before signing in. Account changes invalidate in-flight application of remote responses; an already submitted batch may still reach the server. Deletion markers are retained; do not purge them without an offline-device expiry protocol.
